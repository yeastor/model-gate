# Двойной поиск и Dialogue Manager — 23 октября 2026

Рабочая версия: `mvp-feedback/20261023-v4`. Активный пакет остаётся
`pps-dialogue/20261022-v2`, `service/conversation/policy/pps.v2.json`.

## Порядок работы

1. Обработать сообщение существующими правилами: участник, новый эпизод,
   явные факты, отрицания, исправления, конфликт, изменение процедуры.
2. На содержательном текстовом сообщении выполнить до двух поисков параллельно:
   исходный текст и исходный текст с краткими сведениями текущего эпизода.
   Без дополнительной памяти одинаковые запросы объединяются в один.
3. В краткий текст включать известного участника, ранее установленную тему и
   true/false из активной проекции существующих полей для текущих субъектов.
   null и конфликтные значения не превращать в «нет». Если тема ещё не
   установлена, допустимы последние два описания пользователя того же эпизода
   и субъектов. Текст ответа помощника и неподтверждённая тема статьи не входят.
4. Каждый поиск получает категорию и limit=32, без hardStageId. Поэтому
   предыдущая тема не закрывает поиск в других подтемах PPS.
5. Проверить SHA, category/stage/variant ID, конечный числовой score >= 0.60.
   Объединить кандидатов по variant_id через RRF с k=60; сохранить источник
   direct/contextual. Повтор одного ID внутри списка не увеличивает вес.
6. При установленной по сообщению пользователя процедуре выбирать найденный
   вариант только среди совместимых с известным context и сохраняющих уже
   подтверждённые существенные обстоятельства. Если поиск не предложил такого
   варианта, сохраняется существующий детерминированный выбор движка.
7. Для продолжения уже установленной темы повторно подтверждать её не нужно,
   если результаты поддерживают эту тему. Одинаковая памятка целиком не повторяется.
   Для новой нераспознанной темы сохраняются вопросы Да/Нет/Не знаю и общий
   бюджет двух вопросов. Сходство само по себе не подтверждает ни тему, ни context.
8. Чтобы старая история не делала посторонний запрос полицейским, предложения
   новых тем должны иметь поддержку прямого поиска либо быть зависимым коротким
   продолжением («он…», «говорит…», «просит…» и т. п.). Это эвристика MVP,
   не универсальное понимание языка.

Основной код: `services/category-runtime/service/conversation/retrieval.mjs`.
Подключение и выбор применимого ответа: `service.mjs`. Вопросы маршрутизации:
`routing.mjs`. Обязательная проверка context: прежний `explicit/engine.mjs`.

## Повторы, отказы и сбои

- Нажатия кнопок, «да/нет/не знаю» и запрос повторного показа памятки не вызывают
  новый поиск. Вопрос относится к единственному текущему pending.
- Одинаковый последний запрос с той же памятью использует сохранённые результаты.
  Повтор неразрешённого маршрута не создаёт новый бюджет уточнений.
- Сбой одного поиска позволяет использовать второй. Ожидание каждого ограничено
  10 секундами, запросы параллельны; AbortSignal передаётся до Ollama и Qdrant.
- Ошибочные результаты не кэшируются как успешные: повтор может восстановить поиск.
- Прямо распознанное событие применения силы имеет приоритет над прежней темой
  и найденными похожими, но неподходящими вариантами.
- Данные поискового результата не становятся фактами пользователя. В состоянии
  сохраняются компактные ID/оценки/источники, а не полные тексты найденных ответов.
- Неподобранный ответ и технический сбой поиска различаются. Согласие на отправку
  всей переписки по-прежнему требуется отдельно, автоматической отправки нет.

## Нужно ли перегенерировать пакет

Нет. Изменены алгоритм runtime и его тесты. Формат variant_id, существующие поля
context, исходные NEXT, DOCUMENT, законы и запечатанный JSON категории прежние.
Полный авторский пакет Dialogue Manager и векторы Qdrant перегенерировать не нужно.
При обнаружении новых языковых пробелов добавляются конкретные примеры и точечные
правила с проверкой; такая доработка должна быть отдельной от настройки ранжирования.

## Проверка и ограничения

Команда из корня model-gate:

```powershell
node --test --test-reporter=tap services/category-runtime/service/explicit.test.mjs services/category-runtime/service/validation.test.mjs services/category-runtime/service/conversation/*.test.mjs
```

167 тестов: 162 PASS, 5 прежних необязательных SKIP, 0 FAIL. Включены прежние
681 примеров извлечения и проверки supplemental NEXT. Новые проверки охватывают
двойной поиск, смену темы, совместимость context, исключение неизвестных фактов,
смену эпизода, повторы, частичный сбой, таймаут/отмену и повтор после сбоя.

На локальном сервисе 18110 с настоящей bge-m3 и существующим Qdrant проверены:
остановка → паспорт → зависимое продолжение → сообщение об ударе; посторонний
запрос после этого; общий запрос с неизвестным участником из нового чата и статьи.
Синтетические сессии удалены после проверки. Пользовательские чаты не изменялись.
Наблюдаемая задержка первого тестового сообщения около 3.1 секунды, последующих
поисковых сообщений около 0.45–0.47 секунды; это несколько локальных измерений,
а не нагрузочная проверка или гарантия.

Порог 0.60, окно подсказки 0.08 и RRF — инженерные параметры. Независимый языковой
holdout и нагрузочная проверка здесь не проводились. Изменения развёрнуты локально;
удалённый сервер не обновлялся. Полные доказательства:
`work/dual-retrieval-20261023-v1/tests.txt`, `live-check.json`, `validation-report.json`.
